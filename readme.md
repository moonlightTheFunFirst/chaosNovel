# カオス小説

一人一冊、一度きりの原稿を末尾へ継ぎ足していく共同小説アプリです。本文表示と原稿入力の両方を縦書きにしています。

入室時は**ゲスト**です。「管理者」ボタンでパスワードを入力すると、そのブラウザだけ管理者に昇格します。管理者ログインを使う場合はADMIN_PASSWORDを明示設定してください。未設定ならログインは無効です。管理者は7日間の制限なしで本を作成でき（全体の執筆中冊数の上限は適用）、同じ本へ何度でも投稿でき、本とその投稿履歴を削除できます。一回1〜400字と本の文字数上限・完結ルールは維持します。投稿成功後は本文の最終ページへ戻り、「次の一節を綴る」で続きを書けます。元の原稿は「掲載結果」で確認できます。

## ページ式の読書・執筆

本を開くと、ブラウザ内全画面の読書モードで先頭ページから表示します。本文と原稿は同じ位置・寸法・書体の紙面を使用します。

- 左側のボタン／左キーで次へ、右側のボタン／右キーで前へ。
- 下部のページ移動バーをクリック・ドラッグしてスキップできます。右が先頭、左が末尾です。
- 最終ページに到達すると「次の一節を綴る」が有効になります。一度到達すれば、その本を開いている間は前のページへ戻っても解禁したままです。ページを再読込すると先頭から再開します。
- 白紙・1ページの本は、最初に表示したページが最終ページなので、そのまま執筆できます。完結した本には投稿できません。
- 執筆は本文と同じ紙面上の縦書きtextareaで行います。「閲覧に戻る」でいつでも戻れ、原稿・カーソル位置を保持します。入力中の左右キーはカーソル移動、Enterは改行です。
- 小さい画面で原稿が一枚に収まらない場合は、左右のボタン・移動バーや入力欄のスクロールで原稿の各部分を確認できます。
- 投稿成功後は閲覧モードの末尾へ戻ります。全量掲載なら次の原稿は白紙にし、元原稿は「掲載結果」に保持します。一部掲載・失敗時は原稿を消しません。
- 本の削除と文字数は上部の「メニュー」にあります。

組版は最大40字程度×16列を目安に、画面に合わせて字詰め・列数を減らします。本文のフォントはPC20px、小画面18pxを基本とし、画面に押し込むための過度な縮小は行いません。640文字ずつ文字列を切らず、改行とブラウザの禁則処理（`line-break: strict`）を反映した連続組版を列単位でページ表示します。空白・改行・本文は保持します。画面サイズ変更時は読書位置付近の文字を基準にページを再計算します。移動バーで飛ばせるため、実際に全文を読んだかは判定せず、末尾到達をUI上の解禁条件とします。

管理者権限は署名付きHttpOnly Cookieで12時間保持します。「ゲストに戻る」でサーバー側の失効番号も更新します。コピー済みトークンも失効し、パスワード変更後の再起動でも旧トークンは使えません。管理者ボタンは本棚のヘッダーと読書画面のメニューにあります。ADMIN_MODE環境変数による全員の昇格は廃止しました。createAppのadminModeオプションは既存テスト専用の明示的な注入点です。

## 起動

Node.js **22.13以上** と npm が必要です。検証環境は Windows / Node.js 22.18.0。Node.js 22では組み込みSQLiteの実験的API警告が表示されます。

```powershell
npm ci
npm start
```

http://127.0.0.1:3000 を開きます。`npm start` はブラウザ用JavaScriptをビルドしてからサーバーを起動します。

ポートを変更する場合：

```powershell
$env:PORT = '3100'
npm start
```

`npm run dev` はサーバーを監視して再起動します。フロントエンドのJavaScript変更後は別ターミナルで `npm run build` を実行し、ブラウザを再読込してください。CSSはビルド不要です。

## 設定と保存先

`.env.example` に設定例があります。`.env` の自動読込は行いません。シェルまたはサービスの環境変数で指定します。

| 変数 | 初期値 | 用途 |
| --- | --- | --- |
| `ENABLED_CAPACITIES` | `4000,12000` | ゲストが新規作成できる区分。管理者は設定に関係なく全区分を作成可能 |
| `HOST` | `127.0.0.1` | 待受アドレス |
| `PORT` | `3000` | 待受ポート |
| `DB_PATH` | `./data/novels.sqlite` | SQLiteファイル（起動ディレクトリ基準） |
| `PUBLIC_ORIGIN` | 未設定 | 設定時はそのURLのHostのみ許可。未設定時はlocalhost / 127.0.0.1 / [::1]と実際の待受ポートのみ許可 |
| `TRUST_PROXY` | 未設定 | `1`の場合だけX-Forwarded-Forを使用 |
| `TRUST_PROXY_HOPS` | `1` | 信頼するプロキシの段数（1以上の整数） |
| `COOKIE_SECURE` | 未設定 | HTTPS利用時は `1` |
| `ADMIN_PASSWORD` | 未設定（ログイン無効） | 管理者昇格用。公開環境では12文字以上が必須。必ず長いランダムな値に変更する |
| `COOKIE_SECRET` | 初回に生成してDBへ永続保存 | 明示指定時は32文字以上。DBの鍵より優先し、変更すると既存署名Cookieが失効する |

初回起動時に保存先ディレクトリを作成し、`schema.sql`で基礎テーブルを初期化し、Storeのマイグレーションでバージョン4へ更新します。日時・公開リクエストの追加は `migrations/003-creation.sql` で自動移行します。既存の更新日時は作成日時で補います。既存のバージョン1は `migrations/002-admin.sql` で起動時に自動移行します。本・本文・参加者・冪等性キーは保持し、既存投稿は通常投稿として引き継ぎます。

本、投稿、匿名参加者IDはサーバーDBに保存され、再起動後も残ります。バックアップはサーバー停止後にDBファイルをコピーしてください。実行中のWALファイルを無視して本体だけコピーしないでください。`data/` とDBファイルはGit管理対象外です。

初期版は**単一Node.jsプロセス＋ローカル永続ディスク**で動かす構成です。複数人は同じサーバーへ接続します。複数台のサーバーに別々のSQLiteファイルを配置した構成や、永続ディスクのないホスティングは対象外です。別端末から試す場合はアクセス可能な待受アドレスを設定し、PUBLIC_ORIGINに共有するURLを設定し、同じホスト名・URLを共有してください。

## 確定した扱い

- AGENTS.md第10節の荒らし対策は、ユーザー判断により今回の対象外です。文章らしさの判定、禁止語、AI修正はありません。
- 空白のみ・1文字の原稿も許可します。空文字と401文字以上は拒否します。
- 改行はCRLF/CRをLFに統一します。書記素単位で投稿ごとに文字数を計算し、**各投稿の掲載文字数の合計**を本の文字数とします。投稿同士を連結して再計算しません。
- 書記素分割はクライアント・サーバーで同じ固定バージョンの `graphemer 1.4.0` を利用します。実装のUnicode規則は同ライブラリのUnicode 15準拠です。将来ライブラリを更新する際も、保存済み投稿の文字数を勝手に再計算しない方針です。
- 最後の投稿は残量に収まる先頭の書記素だけを掲載します。「終わり」と書いても文字数上限未満なら完結しません。

## 採用した暫定判断

- ログイン不要。サーバーがランダムな匿名IDを発行し、HttpOnly / SameSite=Lax Cookieで1年間保持します。
- 作成時には最初の一節（1〜400字）が必須です。本と初投稿を同時に公開し、通常利用者は一回分の投稿を消費します。管理者は引き続き投稿できます。タイトルは1〜100字、空白だけは不可。タイトル・長さ・個別投稿の編集削除UIはありません。管理者は本全体を確認ダイアログ経由で削除できます。
- 読書はページ送り方式です。3〜30秒の段階的な更新確認で通知し、「本文に反映」を押すまで表示本文を更新しません。反映時は現在の読書位置付近を保持します。他者の追加で解禁済みの執筆を再ロックしません。
- 原稿と送信中のキーを小説ごとにlocalStorageへ保存します。通信エラーでは同じキー・同じ原稿で再送できます。送信中の原稿は変更不可ですが、選択・コピーできます。通信は15秒でタイムアウトし、結果が不明な場合も再送できます。
- 投稿成功後も元原稿を「掲載結果」に保持し、一部掲載時は未掲載部分を表示します。Cookieと端末の保存領域は独立しています。
- 明朝体は利用端末の游明朝・ヒラギノ明朝等をCSSで指定し、serifへフォールバックします。フォントファイルは配布・外部取得しません。紙の質感はCSSのみです。

## 投稿の整合性

`store.js` の `BEGIN IMMEDIATE` トランザクションで、再送確認、投稿権・完結判定、文字数検証、切り詰め、投稿保存と小説更新を一括確定します。SQLiteはDB全体で書き込みを直列化するため、小説単位の直列化要件を満たす一方、別の本への書き込みも短時間待機します。小規模な初期版の簡素さを優先した判断です。

DBの主な構造：

- `participants`：サーバー発行の匿名ID。
- `novels`：タイトル、上限、合計文字数、確定連番、作成日時、更新日時。
- `posts`：小説・参加者・連番・冪等性キー・元原稿・掲載本文・掲載文字数・確定結果。

通常投稿は `is_admin = 0` の部分一意インデックス `(novel_id, participant_id)` で一冊一回に制限します。管理者投稿はこの回数制限を除外しますが、`(novel_id, sequence)` と `(novel_id, participant_id, request_key)` の一意制約は共通です。保存済み結果を再送時に返すため、後続投稿や完結後の再送も同じ結果になります。同じキーで原稿を変えた場合は409です。失敗・却下では投稿レコードを残さず、投稿権を消費しません。削除は本と全投稿を一つのトランザクションで削除します。

本文とタイトルはDOMの `textContent` で表示します。ユーザー入力をHTMLへ挿入しません。APIのSQLはプレースホルダーを使用し、JSON送信・Origin検証・CSPも設定しています。

## 匿名参加と既知の制限

Cookie削除、別ブラウザ、プライベートブラウズでは別参加者になります。「同一人物」を厳密には識別できません。フィンガープリントやIPによる人物判定は行いません。同じCookieを使う別タブは同じ参加者です。

localStorageが利用できない環境では警告を表示しますが、再読込後の原稿復元は保証できません。端末の保存領域を消去すると下書きも消えます。送信した元原稿（未掲載部分を含む）は再送確認と本人への結果表示のためDBにも保存されます。他の参加者に返す本文は掲載部分だけです。

本棚はカーソル方式、更新通知は差分取得です。長編の初回表示は全文取得で、大量の本・大人数の同時閲覧を前提にした負荷検証は未実施です。

### 最初の一節と本棚

タイトル・長さを選び、縦書きで最初の一節を書いて確認し、「この一節で本を公開する」で初めて本を作成します。下書きと再送用データは端末に保存されます。公開は本と投稿を一つのトランザクションで確定し、同じ参加者・公開キーの再送は同じ本を返します。削除済みの本も再送によって復活しません。

本棚と読書メニューに作成・更新日時を日本時間で表示します。更新日時は本文の新規掲載時のみ変更します。本の名前／作成日時／更新日時の昇順・降順を選べます（初期値は作成日時の新しい順）。名前はサーバー上のUnicode文字列順であり、漢字の読み順ではありません。並び順は端末に保存します。

### 来訪者向けルールと7日間の作成制限

本棚に概要とルール1〜7を表示します。管理者モードでは投稿・作成回数の例外を併記します。

通常利用者は本の公開成功から168時間（7日間）経過するまで次の本を公開できません。判定はサーバー時刻と匿名参加者IDを使用し、本の公開と制限日時を同じ `BEGIN IMMEDIATE` トランザクションで保存します。失敗・確定済みリクエストの再送は期間を延長せず、本を削除しても制限は残ります。他の本への参加と下書きは可能です。画面には次回公開日時（日本時間）を表示します。

`schema.sql` が追加テーブル `creation_limits` を起動時に自動作成します。既存の本・公開履歴から制限を遡及適用しません。DBスキーマバージョン3の既存テーブルに変更はありません。管理者は制限を受けず、管理者としての公開は通常利用者用の制限日時も更新しません。

Cookie削除や別ブラウザによる制限回避は防げません。通常はゲストです。管理者への昇格はパスワード認証したブラウザだけに適用されます。

## レビュー修正：入力容量・通信・Cookie

- 投稿は1〜400書記素に加え **UTF-16長16,000**、タイトルは1〜100書記素に加え **UTF-16長4,000** まで。400個の家族絵文字・肌色付きZWJシーケンスにも余裕を持たせつつ、結合文字の大量付加による巨大クラスタの分割と多重保存を抑えるためです。容量判定は書記素分割の前に行い、クライアントも共通関数で分割を省略して容量超過を表示します。IME変換中に切り捨てません。400字超過の拒否と、作品残量による切り詰めは別処理です。
- 更新確認は `GET /api/novels/:id?after=revision`。新しい投稿のみ取得し、連番・総文字数・revisionの不整合時は全文を再取得します。紙面は「本文に反映」まで変更せず、非表示タブはポーリングを停止、再表示時に即時再開します。
- 匿名CookieはHMAC-SHA256署名付き。閲覧ではparticipantsをINSERTせず、初回投稿・公開のトランザクションで登録します。旧DBに登録済みの未署名ID Cookieは同じIDの署名付きCookieへ移行します。不正署名は新規IDへ置換します。COOKIE_SECRET未設定時の鍵はapp_metaに保存され、再起動後も同じ署名を検証できます。
- 全リクエストでHostを検証し、不許可は421。POST/DELETEはOriginの一致とSec-Fetch-Siteがcross-siteでないことを確認します。逆プロキシではPUBLIC_ORIGINと一致するHostを転送してください。
- 本棚は30件ずつ「さらに読み込む」で取得。APIのlimitは最大100。sort・filterと最後の並び順キー／IDを含むcursorを検証します。レスポンスはbooksとnextCursorです。offsetは受け付けません。
- 削除後の公開キーの再送は404です。削除済みIDを返したり本を復活させたりしません。投稿成功後に本文再取得だけ失敗した場合は、成功と再取得失敗を分けて表示します。

## 2回目レビュー：認証・永続鍵・カーソル

- `ADMIN_PASSWORD`未設定／空なら管理者ログインは503です。コードに既定パスワードはありません。`PUBLIC_ORIGIN`が設定済み、または`COOKIE_SECURE=1`の場合は12文字未満で起動を拒否します。ローカル開発では短い値を明示設定できますが警告します。リリース時は最低長だけに頼らず、必ず十分に長いランダムな値へ変更してください。比較は双方のSHA-256ダイジェストをtimingSafeEqualで行います。
- ログイン失敗は5分の固定窓で集計します。同一IPで5回失敗すると5回目から5分間429（Retry-After付き）。成功時はそのIPの履歴を解除します。全IPの失敗は20回ごとに応答を500ms遅延し、最大3秒です。全体の失敗による一律ロックはなく、ロックされていないIPの正しいパスワードは遅延後に成功します。時刻・遅延はテストで注入できます。
- 通常は`req.socket.remoteAddress`を使用し、X-Forwarded-Forを無視します。`TRUST_PROXY=1`の場合のみ、X-Forwarded-Forの右端から`TRUST_PROXY_HOPS`番目を利用者IPとして使用します（既定1、直結プロキシの手前のIP）。不足・不正なIPはremoteAddressへ戻します。例：利用者, プロキシAというヘッダーで2段設定なら利用者を選びます。プロキシ以外からアプリへ直結できない構成にし、外部から偽装されないよう入口プロキシでヘッダーを上書きしてください。内部プロキシが追記する段数と設定を合わせます。共有IPの利用者は同じ制限を受けます。試行履歴はメモリ上で、再起動で消え、複数プロセス間では共有されません。期限切れを削除し、IP記録は最大10,000件、超過時は登録が古い順に破棄します（破棄されたIPのロックも解除されます）。
- `app_meta`に初回生成の32バイト乱数鍵を保存します。明示的なCOOKIE_SECRET（32文字以上）があればそちらを優先します。`admin_epochs`は参加者ごとの管理者失効番号です。どちらもschema.sqlで自動追加し、既存データは変更しません。DBはGit除外済みで、バックアップには鍵も含まれます。
- 管理者署名鍵はCookie鍵とパスワードのSHA-256からHMACで導出し、トークンには失効番号と12時間の期限を含めます。ログアウト時の失効番号をDBへ保存するため、ログアウト後に再起動しても旧トークンは拒否します。
- 旧バージョンが起動中のメモリにだけ持っていた鍵は復元できません。その鍵で署名されたCookieは今回の移行時に一度無効になります。既存DBにある未署名UUID Cookieは従来どおり移行できます。今回永続化した鍵以降の再起動ではIDと参加制限を維持します。
- 差分取得時はown.sequenceがafterより大きい場合だけownを返します。省略時はクライアントが既存の掲載結果を保持します。初回全文取得は従来どおりownを含みます。
- 本棚はタイトル／作成日時／更新日時とIDを使うカーソルで、昇順・降順に対応します。途中で先頭に本が追加されたり、直前の本が削除されても、未読の既存行をoffsetずれで飛ばしません。カーソルより前に新規追加された本、閲覧中に更新されて並び位置が変わった本は、再読込で取り直してください（一覧全体の固定スナップショットではありません）。
- UTF-16長上限に加えて、原稿・タイトルとも**1書記素クラスタあたり32コードポイント**まで。一般的な家族絵文字、肌色・ZWJ、結合濁点を十分に許容し、過剰な結合文字の密度を抑えるためです。クライアント／サーバー共通のinspectInputで検証します。既存保存本文は書き換えません。長編の初回全文取得量を一定の小容量に保証するものではありません。

## 3回目レビュー：公開設定とタイトル順

公開前にPUBLIC_ORIGIN・COOKIE_SECUREを設定し、ADMIN_PASSWORDを十分に長いランダムな値にしてください。**COOKIE_SECRETは32文字以上の値を環境変数で渡し、DBのバックアップとは別に管理してください。** 本番相当（PUBLIC_ORIGIN設定済み、またはCOOKIE_SECURE=1）でCOOKIE_SECRET未設定なら起動時に警告します。開発時のDB永続鍵による起動は引き続き可能です。

DB鍵から環境変数へ切り替える際は、app_metaのkey=cookie_secretに保存されたvalueと同じ値をCOOKIE_SECRETへ設定すれば、参加者Cookieを引き継げます。値を変えると既存Cookieは無効になります。鍵をログやリポジトリに出力しないでください。

タイトルの並び順は方式(b)、SQLite BINARYのコードポイント順を採用します。画面も「コードポイント昇順／降順」と表記します。数字を数値化せず（本10は本2より先）、ひらがなとカタカナを区別し、読み順への変換はしません。既存データの変換を不要にし、ORDER BYとカーソル条件を同じ比較規則で安定して扱うためです。同名タイトルはID昇順です。

ゲストの「ゲストに戻る」APIはCookieを消すだけでadmin_epochsへ書き込みません。有効な管理者のログアウトでは失効番号を更新します。

## 本の名前の重複防止

管理者を含め、既存の本と同じ比較キーを持つ名前では公開できません。表示用タイトルを変更せず、public/text.jsの共通titleKey関数で次の順に比較キーだけを作ります。

1. CRLF/CRをLFへ統一。
2. Unicode NFKC正規化（全角半角、分解された結合濁点・半濁点を統一）。
3. Default_Ignorable_Code_Pointを除去（ゼロ幅スペース、単語結合子、異体字セレクタ、ZWJ、LRM/RLMなど）。
4. 空白（正規表現の\s）と点字の空白U+2800をすべて除去。
5. toLowerCaseで小文字化。

途中の空白・英字の大小・全角半角・これらの不可視文字は区別しません。ひらがなとカタカナは引き続き区別します。キーが空になる名前は「本の名前を入力してください。」として拒否します。比較ルールはタイトルだけに適用し、本文の表記・内容には適用しません。タイトルの並び順は従来どおり表示文字列のコードポイント順です。

同時公開でも一冊だけ成功します。重複は400の入力エラーとして返し、下書きと原稿を残してタイトル変更・再送を可能にします。失敗時は7日間の作成回数を消費しません。確定済みの同一リクエストの再送は従来どおり成功結果を返します。同名本が一冊でも残っている間は再利用できず、すべて削除した後は名前を再利用できます。

入力時は300ms待って同名確認APIを呼び、入力欄直下に赤いメッセージを表示します。空欄・不正な文字や長さ・重複・確認中・通信失敗では「最初の一節を書く」を無効にします。通信失敗は「名前を再確認」で再試行できます。事前確認は名前の予約ではなく、最終公開時もDBで判定します。

### 使用できない文字

クライアントとサーバーで共通のinspectInputを使い、書記素分割より前に次を拒否します。本文・タイトルを勝手に切り捨てることはありません。

- 投稿：CRLF/CRをLFへ統一後、LF（U+000A）とタブ（U+0009）以外のUnicode制御文字（Cc：U+0000〜U+001F、U+007F〜U+009F）。NULも拒否します。
- タイトル：Ccをすべて拒否します。改行・タブも使えません。
- 両方：対になっていないUTF-16サロゲート、および双方向制御文字U+202A〜U+202EとU+2066〜U+2069。

LRM/RLM（U+200E/U+200F）は保存可能ですが、タイトル比較キーからは除去します。通常の絵文字・ZWJ・結合文字、本文の空白・改行・タブは引き続き許可します（既存の文字数・データ量上限は適用）。エラー時も原稿・下書きは保持します。過去にNULで切り詰められた本文は、この修正では復元できません。既存本文や文字数を自動で書き換えません。

### DBバージョン4への移行

**更新したアプリを起動する前に、サーバーを停止してDBをバックアップしてください。** 停止後にDBファイルをコピーします。WALが残っている場合は本体だけのコピーを避け、整合したバックアップを保管してください。

Store起動時にmigrations/title-keys.jsを実行します。BEGIN IMMEDIATEからCOMMITまで一つのトランザクションで次を行います。失敗した場合は全体をロールバックします。

1. 旧004の式インデックスとトリガーを削除（更新時に旧SQL関数を要求されないよう、行更新より先に削除）。
2. novelsへ通常のtitle_key TEXT列とtitle_legacy_duplicate INTEGER NOT NULL DEFAULT 0列を追加。
3. 既存タイトルからJSでキーを計算。同じキーではcreated_at、idの昇順で最初の一冊を0、それ以外を1として保持。表示用タイトル・本文・投稿履歴は変更しません。
4. title_legacy_duplicate=0の行を対象にtitle_keyの部分一意インデックスを作成。全同名本の検索用にも通常のインデックスを作成。
5. user_version=4、app_metaのtitle_key_versionに2とNodeのUnicodeバージョンを記録。

キー版が異なる起動時は、キー・重複フラグ・一意インデックスを同じトランザクション内で再構築します。旧migrations/004-title-uniqueness.sqlは過去スキーマの参照用で、新しいStoreでは適用しません。独自SQL関数の登録は不要で、通常のSQLiteツールからintegrity_checkや書き込みを実行できます。外部ツールでタイトルを追加・変更するときは同じ比較キーも更新してください（NULLや不正なキーを外部から書けばアプリの重複判定と一致しません）。旧アプリは新しい比較キーを維持できないため、ロールバック時はバックアップと対応するコードを一緒に戻してください。

### 保存と認証

D1では、投稿を読み取ったときのrevisionを保存直前に照合し、参加者登録・投稿・文字数・連番・完結状態を一つの`DB.batch()`トランザクションで確定します。競合時は読み直して最大3回試行し、それでも競合する場合は503で同じ送信キーによる再送を促します。400字超過の拒否と、残量による書記素境界での切り詰めを区別します。公開の7日制限・名前の一意性・冪等性も同じバッチ内で保護します。

新規D1のスキーマは`workers/migrations/0001_initial.sql`です。続けて0002_title_keys.sqlを適用し、JSによるキー再計算を行います。下記の移行手順を参照してください。Node版のschema.sqlや旧移行SQLをD1に適用しないでください。将来比較キーを変える場合は、記録されたtitle_key_versionに対応するD1マイグレーションも追加します。

Workers版ではCOOKIE_SECRETを必須とし、DBに鍵を保存しません。管理者の失効番号とログイン試行回数はD1へ保存し、別のWorkerインスタンスでも共有します。IPはCloudflareが設定するCF-Connecting-IPを使用し、X-Forwarded-For/TRUST_PROXYは使用しません。IPはHMAC化して記録します。ローカルではIPの偽装防止を検証できません。IPごと5回で5分の制限、全体失敗による最大3秒の遅延、最大10,000件の記録制限を維持します。

### 更新確認の間隔と停止条件（Node・Workers共通）

public/sync.jsのPOLL_INTERVALSは3,000 / 6,000 / 12,000 / 30,000ms、POLL_IDLE_MSは600,000msです。更新がない取得のたびに次の段階へ進み、通常の上限は30秒です。執筆中の反応速度を残しつつ、変化のない読書のリクエストを減らすための値です。新しい投稿・執筆開始・入力・投稿や再送後・ページ操作で3秒へ戻します。pointerdown / keydown / scroll / inputを操作として扱います。レスポンス待ちの間は次の取得を重ねません。

10分間操作がないと「更新の確認を止めています」を表示し、次の操作か「更新を確認」で再開します。非表示中は取得せず、再表示時に即時取得します。ただし通信エラー・429・503では段階的に待機し、Retry-After（秒数とHTTP日時の両形式）がある場合は操作・再表示・手動確認でも指定時刻より早く取得しません。完結かつ送信待ちなし、または404では自動取得を停止します。本棚は引き続きポーリングしません。

新しい本文は通知だけを出し、「本文に反映」まで紙面を変更しません。原稿・IME・読書位置の維持、差分の欠落検出と全文再取得は従来どおりです。

リクエスト数は、初回の本文取得や投稿・手動確認・再接続等を除く自動ポーリングの目安です。通信時間も間隔に加わります。

- 常に入力や更新がある場合：最短3秒なので最大約1,200回/時、約28,800回/日。継続操作時の負荷までは解消しません。
- 更新がなく3秒へのリセットが少ない場合：30秒段階で約120回/時。実際は操作で短縮、10分の無操作で停止します。
- 本を開いて操作も更新もない場合：3・9・21秒、その後30秒ごとに計22回取得し、10分で停止。以後は操作するまで0回です。
- 非表示中、完結済みで送信待ちなし：0回。手動確認や頻繁なタブ切替を含む総リクエスト数には固定の上限はありません。

### ツールのバージョン固定

wranglerは4.151.1、miniflareは5.20261012.1-betaに固定しました。選択したWrangler自身がこのMiniflareベータ版を厳密に依存指定しているため、ローカル実行とテストのランタイムを揃えて維持します。テストがMiniflareを直接importするため、偶然のnpm hoistingやWranglerの内部依存へ頼らず直接依存も残します。安定版の別世代への置換は今回行いません。更新時は両者を一緒に検証してください。

### タイトルキー第2版とD1の更新手順

追加の除去文字はU+2800（点字の空白）のみです。U+115F/U+1160/U+3164/U+FFA0はNFKCとDefault_Ignorableの処理で既に除去されることをテストしています。見た目が似る別の文字（ラテン文字aとキリル文字а等）は区別します。本文にはこの比較ルールを適用しません。

TITLE_KEY_VERSIONは2です。Nodeは `2:${process.versions.unicode}` を保存して照合し、ルールまたはUnicode版が変われば起動時に全件再計算します。schema.sqlはuser_versionを変更せず、マイグレーションが最新版4への更新を担当します。

D1の0002はtitle_key_v2・title_legacy_duplicateを追加し、既存の外部キーや本文を保ったまま比較列を切り替えます。旧title_keyのSQLite自動一意制約を壊さず残すため、新規行の旧列には本のIDを入れ、名前の検索・事前確認・一意判定には使いません。新列は非重複行だけの一意インデックスを使います。同じキーではcreated_at、idが最も古い一冊を代表にし、それ以外も削除せず保持します。残った同名本をすべて削除すれば名前を再利用できます。

**移行前にDBをバックアップし、旧・新Workerを含むすべての書き込みを停止してください。** ローカルでは開発サーバーをCtrl+Cで停止します。ローカル一括手順は `npm run workers:setup` です。これはSQLマイグレーションの後に `npm run workers:rekey -- --local` を実行します。再計算だけなら後者を単独実行できます。

将来の本番移行は次の順序です（今回、本番には実行していません）。

1. メンテナンス状態で書き込みを停止し、D1をexportしてバックアップ。
2. `npx wrangler d1 migrations apply chaos-novel-db --remote` で0002を適用。
3. `npm run workers:rekey -- --remote --maintenance-confirmed` を実行。
4. キー版、行数、同名確認を検証して、新版Workerで書き込みを再開。

再計算スクリプトは最初にキー版をpendingにし、新規本のINSERTをトリガーで止めます。全件のid/title/created_atを読み、共有titleKeyでJS計算し、更新SQLファイルをWranglerで適用します。完了時だけキー版を `2:<計算に使ったNodeのUnicode版>` にします。失敗時は書き込みを再開せず、原因を修正して再実行してください。生成SQLはGit対象外の.wrangler内に保存されます。既存本文は変更しません。

WorkersのUnicodeデータはNodeと別に更新され得ます。D1保存値は再計算したNodeの版の記録であり、Workersとの一致を自動保証するものではありません。**Node・Wrangler/workerd・Workers compatibility_dateを更新するときは、移行用Nodeも対応するUnicode版に揃え、ローカルとWorkersのタイトル変形テストを通してから、書き込み停止下で全件再計算してください。** Unicode版が揃わない状態では公開を進めないでください。


## 執筆中の本の上限

執筆中（count < capacity）の本は、サイト全体で既定30冊までです。完結した本は保存・閲覧できますが枠に数えません。管理者もこの上限の対象です。満杯なら公開時に409を返し、いずれかの本が完結するか管理者が削除すると枠が空きます。タイトル・原稿の下書きは可能で、拒否時も消しません。既存の7日間制限、管理者の7日間制限免除、名前の重複判定は維持します。

MAX_ACTIVE_NOVELSに1以上の整数を設定して変更できます。Node版は起動環境変数、Workers本番はwrangler.jsoncのトップレベルvars、ローカルはenv.local.varsまたは.dev.vars.localへ設定し、再起動してください。未指定は30、不正値は設定エラーです。同じDBを使うインスタンスは同じ値で運用してください。上限を既存冊数より下げても本は削除せず、新規公開だけを停止します。

本棚と作成画面に状態を表示し、作成画面の「公開条件を再確認」で完結後の空きを確認できます。事前確認は枠の予約ではありません。確定済みの公開の再送は満杯でも同じ結果を返します。NodeではBEGIN IMMEDIATE内で判定、D1では公開バッチ内のCHECK制約で再判定し、競合時は読み直します。却下時は本・投稿・7日制限を消費しません。

完結済みの本を数え続けないよう、執筆中の行だけの部分インデックスを追加しました。Nodeは起動時にschema.sqlから作成します。D1はworkers/migrations/0003_active_novels.sqlを適用します。ローカルはサーバー停止後に `npx wrangler d1 migrations apply chaos-novel-local --local --env local` を実行してください。今回の変更で既存データやタイトルキーの再計算は不要です。

## 管理者による執筆終了

管理者は本棚の各本、または読書画面のメニューにある「執筆を終了」から、確認画面を経て強制終了できます。本文・実文字数・掲載順・投稿履歴をそのまま保持し、終了後は管理者を含め追加投稿できません。再開機能はありません。操作は再送可能で、確定済み投稿の冪等再送も従来どおり結果を返します。

終了した本は本棚の「執筆終了」で絞り込めます。専用の別ページは設けず、各本のURLで全文を閲覧します。状態は「執筆終了」に統一し、理由として「文字数到達」または「管理者による終了」を別に表示します。強制終了も執筆中30冊の枠から除外します。

終了状態はnovel_closuresに保存し、本文のcountやrevisionを水増ししません。Nodeではトランザクション、D1ではバッチ処理と投稿保存直前の終了状態チェックにより、終了と投稿の競合を処理します。投稿が先に確定すればその分も保持し、終了が先なら投稿は409で拒否します。差分APIは同じrevisionでも終了状態を返し、クライアントは本文・原稿・読書位置を変更せず通知します。送信待ちがなければ終了後のポーリングを停止します。

Nodeは起動時にテーブルを追加します。Workersは0004_novel_closures.sqlを適用してください。終了状態は永続化され、本の削除時に一緒に削除されます。ローカルではサーバー停止後に `npx wrangler d1 migrations apply chaos-novel-local --local --env local` を実行します。

本棚の「新しい本をつくる」は全体上限に到達するとグレーアウトして操作できません。マウスオーバーまたはキーボードフォーカスで「これ以上本を作成できません。先に他の本の執筆を完了させてください。」を表示します。冊数の確認中・取得失敗時も無効です。完結・削除後の本棚再取得で空きがあれば有効に戻ります。

## 執筆状態と閲覧向けレイアウト

本棚の状態表示を20px、読書画面を18pxに拡大し、「執筆中／執筆終了」に統一しました。終了理由は「文字数到達」「管理者による終了」を別に表示します。終了済みの本棚カードには進捗バーを表示せず、全掲載文字数と「この本を読む」を表示します。執筆中は残り文字数と「続きを読む・書く」を表示します。

読書画面の終了済み状態では新規執筆・投稿確認ボタンを隠し、ページ送りを中心に配置します。保存した原稿・掲載結果・コピー・送信待ちの再確認は引き続き利用できます。終了通知で原稿やページ位置を自動的に切り替えません。

## 新規作成で選べる長さ

ゲストは既定で短編4,000字と中編12,000字のみ新規公開できます。ENABLED_CAPACITIESはカンマ区切りで指定し、4000・12000・40000だけを受け付けます。空文字・空要素・重複・それ以外の値は設定エラーです。前後の空白は許容し、画面では短い順に表示します。NodeはStore初期化時、Workersは環境変数を利用できるAPIリクエストのStore初期化時に検証します。

Nodeで長編をゲストにも解放するには環境変数ENABLED_CAPACITIESを`4000,12000,40000`へ変更して再起動します。Workersの手順は上記の区分設定を参照してください。同じDBを使用するインスタンスは設定を揃えてください。

**管理者は設定に関係なく短編・中編・長編を作成できます。** 更新されたAGENTS.mdの運用方針を基本とし、「管理者にも制限する」という箇所のみ、その後のユーザー指示（管理者は全区分を選択可能）を優先しています。AGENTS.mdの確定仕様本文は変更していません。

制限は新規公開だけに適用し、既存の長編の閲覧・投稿・完結・本棚表示には影響しません。区分の字数とDBのCHECK制約は維持し、マイグレーションは不要です。管理者の冊数上限や執筆終了など、他の制限は変わりません。確定済み公開の同じキー・同じ内容による再送は、設定でその区分を停止しても同じIDを返します。

/api/sessionのcreation.capacitiesは、その利用者が新規作成できる区分の配列です。選べなくなった区分の下書き・送信待ちは、タイトルと本文を保持して、許可された最短区分へ戻し、変更を表示します。送信待ちは解除して下書きとして保存します。確定済みか不明な送信待ちを変更した場合は、本棚に前回の本がないか確認してから公開してください。
