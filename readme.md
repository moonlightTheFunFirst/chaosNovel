# カオス小説

一人一冊、一度きりの原稿を末尾へ継ぎ足していく共同小説アプリです。本文表示と原稿入力の両方を縦書きにしています。

入室時は**ゲスト**です。「管理者」ボタンでパスワードを入力すると、そのブラウザだけ管理者に昇格します。管理者ログインを使う場合はADMIN_PASSWORDを明示設定してください。未設定ならログインは無効です。管理者は本を何冊でも作成でき、同じ本へ何度でも投稿でき、本とその投稿履歴を削除できます。一回1〜400字と本の文字数上限・完結ルールは維持します。投稿成功後は本文の最終ページへ戻り、「次の一節を綴る」で続きを書けます。元の原稿は「掲載結果」で確認できます。

## ページ式の読書・執筆

本を開くと、ブラウザ内全画面の読書モードで先頭ページから表示します。本文と原稿は同じ位置・寸法・書体の紙面を使用します。

- 左側のボタン／左キーで次へ、右側のボタン／右キーで前へ。
- 下部のページ移動バーをクリック・ドラッグしてスキップできます。右が先頭、左が末尾です。
- 最終ページに到達すると「次の一節を綴る」が有効になります。一度到達すれば、その本を開いている間は前のページへ戻っても解禁したままです。ページを再読込すると先頭から再開します。
- 白紙・1ページの本は、最初に表示したページが最終ページなので、そのまま執筆できます。完結した本には投稿できません。
- 執筆は本文と同じ紙面上の縦書きtextareaで行います。「閲覧に戻る」でいつでも戻れ、原稿・カーソル位置を保持します。入力中の左右キーはカーソル移動、Enterは改行です。
- 小さい画面で原稿が一枚に収まらない場合は、左右のボタン・移動バーや入力欄のスクロールで原稿の各部分を確認できます。
- 投稿成功後は閲覧モードの末尾へ戻ります。全量掲載なら次の原稿は白紙にし、元原稿は「掲載結果」に保持します。一部掲載・失敗時は原稿を消しません。
- 本の削除と文字数は上部の「メニュー」にあります。

組版は最大40字程度×16列を目安に、画面に合わせて字詰め・列数を減らします。本文のフォントはPC20px、小画面18pxを基本とし、画面に押し込むための過度な縮小は行いません。640文字ずつ文字列を切らず、改行とブラウザの禁則処理（`line-break: strict`）を反映した連続組版を列単位でページ表示します。空白・改行・本文は保持します。画面サイズ変更時は読書位置付近の文字を基準にページを再計算します。移動バーで飛ばせるため、実際に全文を読んだかは判定せず、末尾到達をUI上の解禁条件とします。

管理者権限は署名付きHttpOnly Cookieで12時間保持します。「ゲストに戻る」でサーバー側の失効番号も更新します。コピー済みトークンも失効し、パスワード変更後の再起動でも旧トークンは使えません。管理者ボタンは本棚のヘッダーと読書画面のメニューにあります。ADMIN_MODE環境変数による全員の昇格は廃止しました。createAppのadminModeオプションは既存テスト専用の明示的な注入点です。

## 起動

Node.js **22.13以上** と npm が必要です。検証環境は Windows / Node.js 22.18.0。Node.js 22では組み込みSQLiteの実験的API警告が表示されます。

```powershell
npm ci
npm start
```

http://127.0.0.1:3000 を開きます。`npm start` はブラウザ用JavaScriptをビルドしてからサーバーを起動します。

ポートを変更する場合：

```powershell
$env:PORT = '3100'
npm start
```

`npm run dev` はサーバーを監視して再起動します。フロントエンドのJavaScript変更後は別ターミナルで `npm run build` を実行し、ブラウザを再読込してください。CSSはビルド不要です。

## 設定と保存先

`.env.example` に設定例があります。`.env` の自動読込は行いません。シェルまたはサービスの環境変数で指定します。

| 変数 | 初期値 | 用途 |
| --- | --- | --- |
| `HOST` | `127.0.0.1` | 待受アドレス |
| `PORT` | `3000` | 待受ポート |
| `DB_PATH` | `./data/novels.sqlite` | SQLiteファイル（起動ディレクトリ基準） |
| `PUBLIC_ORIGIN` | 未設定 | 設定時はそのURLのHostのみ許可。未設定時はlocalhost / 127.0.0.1 / [::1]と実際の待受ポートのみ許可 |
| `TRUST_PROXY` | 未設定 | `1`の場合だけX-Forwarded-Forを使用 |
| `TRUST_PROXY_HOPS` | `1` | 信頼するプロキシの段数（1以上の整数） |
| `COOKIE_SECURE` | 未設定 | HTTPS利用時は `1` |
| `ADMIN_PASSWORD` | 未設定（ログイン無効） | 管理者昇格用。公開環境では12文字以上が必須。必ず長いランダムな値に変更する |
| `COOKIE_SECRET` | 初回に生成してDBへ永続保存 | 明示指定時は32文字以上。DBの鍵より優先し、変更すると既存署名Cookieが失効する |

初回起動時に保存先ディレクトリを作成し、`schema.sql` によりバージョン3のDBを初期化します。日時・公開リクエストの追加は `migrations/003-creation.sql` で自動移行します。既存の更新日時は作成日時で補います。既存のバージョン1は `migrations/002-admin.sql` で起動時に自動移行します。本・本文・参加者・冪等性キーは保持し、既存投稿は通常投稿として引き継ぎます。

本、投稿、匿名参加者IDはサーバーDBに保存され、再起動後も残ります。バックアップはサーバー停止後にDBファイルをコピーしてください。実行中のWALファイルを無視して本体だけコピーしないでください。`data/` とDBファイルはGit管理対象外です。

初期版は**単一Node.jsプロセス＋ローカル永続ディスク**で動かす構成です。複数人は同じサーバーへ接続します。複数台のサーバーに別々のSQLiteファイルを配置した構成や、永続ディスクのないホスティングは対象外です。別端末から試す場合はアクセス可能な待受アドレスを設定し、PUBLIC_ORIGINに共有するURLを設定し、同じホスト名・URLを共有してください。

## 確定した扱い

- AGENTS.md第10節の荒らし対策は、ユーザー判断により今回の対象外です。文章らしさの判定、禁止語、AI修正はありません。
- 空白のみ・1文字の原稿も許可します。空文字と401文字以上は拒否します。
- 改行はCRLF/CRをLFに統一します。書記素単位で投稿ごとに文字数を計算し、**各投稿の掲載文字数の合計**を本の文字数とします。投稿同士を連結して再計算しません。
- 書記素分割はクライアント・サーバーで同じ固定バージョンの `graphemer 1.4.0` を利用します。実装のUnicode規則は同ライブラリのUnicode 15準拠です。将来ライブラリを更新する際も、保存済み投稿の文字数を勝手に再計算しない方針です。
- 最後の投稿は残量に収まる先頭の書記素だけを掲載します。「終わり」と書いても文字数上限未満なら完結しません。

## 採用した暫定判断

- ログイン不要。サーバーがランダムな匿名IDを発行し、HttpOnly / SameSite=Lax Cookieで1年間保持します。
- 作成時には最初の一節（1〜400字）が必須です。本と初投稿を同時に公開し、通常利用者は一回分の投稿を消費します。管理者は引き続き投稿できます。タイトルは1〜100字、空白だけは不可。タイトル・長さ・個別投稿の編集削除UIはありません。管理者は本全体を確認ダイアログ経由で削除できます。
- 読書はページ送り方式です。3秒ごとの更新確認で通知し、「本文に反映」を押すまで表示本文を更新しません。反映時は現在の読書位置付近を保持します。他者の追加で解禁済みの執筆を再ロックしません。
- 原稿と送信中のキーを小説ごとにlocalStorageへ保存します。通信エラーでは同じキー・同じ原稿で再送できます。送信中の原稿は変更不可ですが、選択・コピーできます。通信は15秒でタイムアウトし、結果が不明な場合も再送できます。
- 投稿成功後も元原稿を「掲載結果」に保持し、一部掲載時は未掲載部分を表示します。Cookieと端末の保存領域は独立しています。
- 明朝体は利用端末の游明朝・ヒラギノ明朝等をCSSで指定し、serifへフォールバックします。フォントファイルは配布・外部取得しません。紙の質感はCSSのみです。

## 投稿の整合性

`store.js` の `BEGIN IMMEDIATE` トランザクションで、再送確認、投稿権・完結判定、文字数検証、切り詰め、投稿保存と小説更新を一括確定します。SQLiteはDB全体で書き込みを直列化するため、小説単位の直列化要件を満たす一方、別の本への書き込みも短時間待機します。小規模な初期版の簡素さを優先した判断です。

DBの主な構造：

- `participants`：サーバー発行の匿名ID。
- `novels`：タイトル、上限、合計文字数、確定連番、作成日時、更新日時。
- `posts`：小説・参加者・連番・冪等性キー・元原稿・掲載本文・掲載文字数・確定結果。

通常投稿は `is_admin = 0` の部分一意インデックス `(novel_id, participant_id)` で一冊一回に制限します。管理者投稿はこの回数制限を除外しますが、`(novel_id, sequence)` と `(novel_id, participant_id, request_key)` の一意制約は共通です。保存済み結果を再送時に返すため、後続投稿や完結後の再送も同じ結果になります。同じキーで原稿を変えた場合は409です。失敗・却下では投稿レコードを残さず、投稿権を消費しません。削除は本と全投稿を一つのトランザクションで削除します。

本文とタイトルはDOMの `textContent` で表示します。ユーザー入力をHTMLへ挿入しません。APIのSQLはプレースホルダーを使用し、JSON送信・Origin検証・CSPも設定しています。

## 匿名参加と既知の制限

Cookie削除、別ブラウザ、プライベートブラウズでは別参加者になります。「同一人物」を厳密には識別できません。フィンガープリントやIPによる人物判定は行いません。同じCookieを使う別タブは同じ参加者です。

localStorageが利用できない環境では警告を表示しますが、再読込後の原稿復元は保証できません。端末の保存領域を消去すると下書きも消えます。送信した元原稿（未掲載部分を含む）は再送確認と本人への結果表示のためDBにも保存されます。他の参加者に返す本文は掲載部分だけです。

本棚はカーソル方式、更新通知は差分取得です。長編の初回表示は全文取得で、大量の本・大人数の同時閲覧を前提にした負荷検証は未実施です。

### 最初の一節と本棚

タイトル・長さを選び、縦書きで最初の一節を書いて確認し、「この一節で本を公開する」で初めて本を作成します。下書きと再送用データは端末に保存されます。公開は本と投稿を一つのトランザクションで確定し、同じ参加者・公開キーの再送は同じ本を返します。削除済みの本も再送によって復活しません。

本棚と読書メニューに作成・更新日時を日本時間で表示します。更新日時は本文の新規掲載時のみ変更します。本の名前／作成日時／更新日時の昇順・降順を選べます（初期値は作成日時の新しい順）。名前はサーバー上のUnicode文字列順であり、漢字の読み順ではありません。並び順は端末に保存します。

### 来訪者向けルールと7日間の作成制限

本棚に概要とルール1〜7を表示します。管理者モードでは投稿・作成回数の例外を併記します。

通常利用者は本の公開成功から168時間（7日間）経過するまで次の本を公開できません。判定はサーバー時刻と匿名参加者IDを使用し、本の公開と制限日時を同じ `BEGIN IMMEDIATE` トランザクションで保存します。失敗・確定済みリクエストの再送は期間を延長せず、本を削除しても制限は残ります。他の本への参加と下書きは可能です。画面には次回公開日時（日本時間）を表示します。

`schema.sql` が追加テーブル `creation_limits` を起動時に自動作成します。既存の本・公開履歴から制限を遡及適用しません。DBスキーマバージョン3の既存テーブルに変更はありません。管理者は制限を受けず、管理者としての公開は通常利用者用の制限日時も更新しません。

Cookie削除や別ブラウザによる制限回避は防げません。通常はゲストです。管理者への昇格はパスワード認証したブラウザだけに適用されます。

## レビュー修正：入力容量・通信・Cookie

- 投稿は1〜400書記素に加え **UTF-16長16,000**、タイトルは1〜100書記素に加え **UTF-16長4,000** まで。400個の家族絵文字・肌色付きZWJシーケンスにも余裕を持たせつつ、結合文字の大量付加による巨大クラスタの分割と多重保存を抑えるためです。容量判定は書記素分割の前に行い、クライアントも共通関数で分割を省略して容量超過を表示します。IME変換中に切り捨てません。400字超過の拒否と、作品残量による切り詰めは別処理です。
- 更新確認は `GET /api/novels/:id?after=revision`。新しい投稿のみ取得し、連番・総文字数・revisionの不整合時は全文を再取得します。紙面は「本文に反映」まで変更せず、非表示タブはポーリングを停止、再表示時に即時再開します。
- 匿名CookieはHMAC-SHA256署名付き。閲覧ではparticipantsをINSERTせず、初回投稿・公開のトランザクションで登録します。旧DBに登録済みの未署名ID Cookieは同じIDの署名付きCookieへ移行します。不正署名は新規IDへ置換します。COOKIE_SECRET未設定時の鍵はapp_metaに保存され、再起動後も同じ署名を検証できます。
- 全リクエストでHostを検証し、不許可は421。POST/DELETEはOriginの一致とSec-Fetch-Siteがcross-siteでないことを確認します。逆プロキシではPUBLIC_ORIGINと一致するHostを転送してください。
- 本棚は30件ずつ「さらに読み込む」で取得。APIのlimitは最大100。sort・filterと最後の並び順キー／IDを含むcursorを検証します。レスポンスはbooksとnextCursorです。offsetは受け付けません。
- 削除後の公開キーの再送は404です。削除済みIDを返したり本を復活させたりしません。投稿成功後に本文再取得だけ失敗した場合は、成功と再取得失敗を分けて表示します。

## 2回目レビュー：認証・永続鍵・カーソル

- `ADMIN_PASSWORD`未設定／空なら管理者ログインは503です。コードに既定パスワードはありません。`PUBLIC_ORIGIN`が設定済み、または`COOKIE_SECURE=1`の場合は12文字未満で起動を拒否します。ローカル開発では短い値を明示設定できますが警告します。リリース時は最低長だけに頼らず、必ず十分に長いランダムな値へ変更してください。比較は双方のSHA-256ダイジェストをtimingSafeEqualで行います。
- ログイン失敗は5分の固定窓で集計します。同一IPで5回失敗すると5回目から5分間429（Retry-After付き）。成功時はそのIPの履歴を解除します。全IPの失敗は20回ごとに応答を500ms遅延し、最大3秒です。全体の失敗による一律ロックはなく、ロックされていないIPの正しいパスワードは遅延後に成功します。時刻・遅延はテストで注入できます。
- 通常は`req.socket.remoteAddress`を使用し、X-Forwarded-Forを無視します。`TRUST_PROXY=1`の場合のみ、X-Forwarded-Forの右端から`TRUST_PROXY_HOPS`番目を利用者IPとして使用します（既定1、直結プロキシの手前のIP）。不足・不正なIPはremoteAddressへ戻します。例：利用者, プロキシAというヘッダーで2段設定なら利用者を選びます。プロキシ以外からアプリへ直結できない構成にし、外部から偽装されないよう入口プロキシでヘッダーを上書きしてください。内部プロキシが追記する段数と設定を合わせます。共有IPの利用者は同じ制限を受けます。試行履歴はメモリ上で、再起動で消え、複数プロセス間では共有されません。期限切れを削除し、IP記録は最大10,000件、超過時は登録が古い順に破棄します（破棄されたIPのロックも解除されます）。
- `app_meta`に初回生成の32バイト乱数鍵を保存します。明示的なCOOKIE_SECRET（32文字以上）があればそちらを優先します。`admin_epochs`は参加者ごとの管理者失効番号です。どちらもschema.sqlで自動追加し、既存データは変更しません。DBはGit除外済みで、バックアップには鍵も含まれます。
- 管理者署名鍵はCookie鍵とパスワードのSHA-256からHMACで導出し、トークンには失効番号と12時間の期限を含めます。ログアウト時の失効番号をDBへ保存するため、ログアウト後に再起動しても旧トークンは拒否します。
- 旧バージョンが起動中のメモリにだけ持っていた鍵は復元できません。その鍵で署名されたCookieは今回の移行時に一度無効になります。既存DBにある未署名UUID Cookieは従来どおり移行できます。今回永続化した鍵以降の再起動ではIDと参加制限を維持します。
- 差分取得時はown.sequenceがafterより大きい場合だけownを返します。省略時はクライアントが既存の掲載結果を保持します。初回全文取得は従来どおりownを含みます。
- 本棚はタイトル／作成日時／更新日時とIDを使うカーソルで、昇順・降順に対応します。途中で先頭に本が追加されたり、直前の本が削除されても、未読の既存行をoffsetずれで飛ばしません。カーソルより前に新規追加された本、閲覧中に更新されて並び位置が変わった本は、再読込で取り直してください（一覧全体の固定スナップショットではありません）。
- UTF-16長上限に加えて、原稿・タイトルとも**1書記素クラスタあたり32コードポイント**まで。一般的な家族絵文字、肌色・ZWJ、結合濁点を十分に許容し、過剰な結合文字の密度を抑えるためです。クライアント／サーバー共通のinspectInputで検証します。既存保存本文は書き換えません。長編の初回全文取得量を一定の小容量に保証するものではありません。

## 3回目レビュー：公開設定とタイトル順

公開前にPUBLIC_ORIGIN・COOKIE_SECUREを設定し、ADMIN_PASSWORDを十分に長いランダムな値にしてください。**COOKIE_SECRETは32文字以上の値を環境変数で渡し、DBのバックアップとは別に管理してください。** 本番相当（PUBLIC_ORIGIN設定済み、またはCOOKIE_SECURE=1）でCOOKIE_SECRET未設定なら起動時に警告します。開発時のDB永続鍵による起動は引き続き可能です。

DB鍵から環境変数へ切り替える際は、app_metaのkey=cookie_secretに保存されたvalueと同じ値をCOOKIE_SECRETへ設定すれば、参加者Cookieを引き継げます。値を変えると既存Cookieは無効になります。鍵をログやリポジトリに出力しないでください。

タイトルの並び順は方式(b)、SQLite BINARYのコードポイント順を採用します。画面も「コードポイント昇順／降順」と表記します。数字を数値化せず（本10は本2より先）、ひらがなとカタカナを区別し、読み順への変換はしません。既存データの変換を不要にし、ORDER BYとカーソル条件を同じ比較規則で安定して扱うためです。同名タイトルはID昇順です。

ゲストの「ゲストに戻る」APIはCookieを消すだけでadmin_epochsへ書き込みません。有効な管理者のログアウトでは失効番号を更新します。
